# 作者及编辑指南

## 1. 目的及范围

当您为 Win.Win 人工智能盲点指南进行 **撰写、编辑、自定义、本地化、审核、验证、发布或维护** 时，请使用本页。它是套件层面的撰写权威，涵盖结构、术语、控制强度、文件角色、交叉参照、本地化、验证、维护及变更报告。

在本作者及编辑指南中，**Win.Win 人工智能盲点指南（BSG）** 及 **Win.Win 人工智能应用案例指南（UCG）** 在此定义后可分别缩写为 **BSG** 及 **UCG**。BSG 及 UCG 只供撰写、维护、审核、验证及证据工作使用。不要假设面向读者的文件已定义或应使用其中任何一个缩写。

本指南适用于 Win.Win 维护者、调整 BSG 的机构、作者及编辑、审核者及专门领域人士、翻译者及双语审核者，以及支持受控工作的人工智能助理。

其范围是本指南内容的治理及维护。它不替换 [[如何使用本指南]] 中面向读者的操作指引、[[指南范围及定位]] 中的范围声明、[[术语表]] 中的规范术语，或本指南可能要求读者使用的任务层面专门领域流程。

BSG 的指定受众是个人、教会、非营利机构，以及中小企业。其他读者可按其情境调整本指南，但不得削弱强制控制。

### 1.1 目的忠实度及读者结果

Win.Win 人工智能盲点指南帮助读者识别这类情况：人工智能辅助输出可能看起来清楚、完整、平衡或有信心，但人工智能无法可靠地看见、保留、判断、核实、授权，或为负责人必须处理的事项承担责任。

人工智能盲点比未明说的语境更广。本指南的广泛模型包括任务依据差距，以及涉及真实或本地理解、判断、权限、问责、独立核实、受众影响、专业直觉、运营记忆、后果意识，或其他人工智能无法可靠掌握事项的更广边界。

Win.Win 人工智能盲点指南目前的详细重点是识别及引导提取未明说的语境。

关于检索及提取已批准来源、可表述性、安全转换、仅由人处理、核实、由承担责任或专门领域人士审核、停止及升级处理的支持指引，可帮助读者在识别或带出情境后采取行动。不要把这些支持指引描述为同等层级的详细模组。

本指南把引导提取、检索、提取、安全处理、审核、核实、路径处理、停止、升级处理及选用保留视为彼此相关但 **在架构上不同的功能**。视乎情境，一个项目可能是规范控制、规范方法、控制内的行动、处理决定、审核活动、问责路径、升级处理行动或保留决定。不要把每项降低风险的活动都称为控制。一个广泛问题、一份完整来源资料包或一个详细提示词，都不能替换权限、独立核实、合资格判断、承担责任的审核、升级处理或停止规则。

审核 BSG 是否达成其目的时，请检查读者能否：
- 识别相关盲点；
- 找出负责人必须解决的问题；
- 在适当时查找或引导提取合适语境；
- 为目前任务选择安全路径；
- 让具合适适任性的审核者参与；以及
- 在问题无法安全解决时停止或升级处理。

> [!important] 所有者目的及预期读者结果
> 面向读者的 BSG 内容，是为大约 20–80 岁的一般成人设计；他们熟悉使用生成式人工智能（GenAI），但未必熟悉人工智能治理术语，亦可能倾向信任流畅、精致或有信心的人工智能输出。
>
> 设计本指南时，应令读者在使用后更有可能记住 **人工智能盲点** 的核心概念、识别重要的人工智能盲点风险模式，并记住至少一项相关缓解路径，例如控制、方法、问责路径或详细指引。如果读者日后记不起确切风险名称或解决方法，最低限度的预期结果是他们能识别 **「这可能是人工智能盲点」**，并知道 **Win.Win 人工智能盲点指南** 是可返回查阅更多资料及实用缓解指引的地方。

撰写或审核面向读者的内容时，使用以下所有者目的验收准则：

1. **术语一致性** — 同一概念使用一个稳定的受控名称，让读者日后能再次识别。简单易明的导航可解释受控术语，但不得创建竞争名称。
2. **一般成人可理解程度** — 一般 GenAI 用户应可在不需要先研读术语表的情况下，理解关键消息及下一步行动。如有需要，在首次使用不熟悉的受控术语时，加入简短的即场解释。
3. **意识加缓解** — 每项规范人工智能盲点风险都必须帮助读者理解可能出现什么问题、为何重要，以及下一步应做什么。如未提供详细缓解指引，至少指出一项相关控制、方法、问责路径或其他已批准的继续路径。

把读者识别及记忆视为设计目标，而不是保证。不要声明本指南可确保读者会记住什么。

#### 新读者清晰度及翻译稳健性

对每份非 README 的面向读者页面，保留原有实质意图，但呈现方式应让新读者不需要拆解复杂英文句式，也能理解应采取的行动。

使用以下默认做法：
- 如可能不清楚由谁行动，明确指出行动者；
- 条件使用 **if** 或 **when**；**where** 主要保留给位置，或明确的地方／来源问题；
- 除非被询问的人或系统已清楚指明，否则不要单独使用 `Ask:`、`ask what`、`ask whether` 或类似文字；
- 行动指示以清楚动词开始，例如 **identify、check、consult、retrieve、verify、route、decide、stop** 或 **record**；
- 如由人掌握的语境、记录中的语境、人工智能处理及仅由人处理使用不同路径，请分开说明；
- 如项目符号能减低认知负荷，对平行选项、准则、路径或后果使用项目符号；
- 如次序重要，使用编号步骤；
- 如以段落能更清楚表达概念之间的关系，保留段落形式；
- 如分组代表有意义的关系、选择决定或实施选项，不要使用没有解释的纯名称清单；应简要说明 **为何每项相关、何时适用或它担当什么角色**；
- 如只是库存清单、索引、导航辅助，或其他不需要解释项目关系的情况，纯清单仍可接受；
- 在可行情况下，每句优先表达一项主要行动或判断；以及
- 如指涉对象可能有多于一种理解，避免使用 **this、it、they** 或 **that** 等含糊代名词。

**行动者－行动－对象／接收者－条件－路径原则**

对每项指示、决策规则、审核提示或路径陈述，文字本身必须足以还原其操作逻辑。在相关时，新读者应能识别：

- **行动者** — 谁采取行动；
- **行动** — 他们做什么；
- **对象或接收者** — 他们对什么或谁采取行动、核对、咨询、提问、核实、转交或审核；
- **条件** — 行动在何时或什么情况下适用；以及
- **路径** — 事项是通过人工智能、人、已批准记录、仅由人处理、核实、承担责任的审核或升级处理。

不要依赖作者记忆中的意图去补足其中任何元素。已发布文字不需要使用上述标签，但读者必须能在不需要猜测的情况下还原逻辑。

不要把概念、控制、方法或问责路径拟人化，好像它本身就是执行审核行动的人。避免使用 `Reviewer standing asks whether...`、`Materiality asks what...` 或 `Source location asks where...` 等文字。优先使用以下形式之一：

- 直接陈述概念，例如 `Reviewer standing concerns whether...`；
- 陈述审核者行动，例如 `Check whether...`；或
- 明确标示诊断问题，例如 `Use this question: ...`。

使用 **ask** 时，如情境尚未令双方清楚无疑，应同时写清楚：**谁提问 + 向谁或什么提问 + 希望取得什么资料**。仅因作者知道预期提问者是谁，并不足以令 `Ask what...` 或 `ask whether...` 变得清楚。

作为审核诊断，如有帮助，可把每项实质指示简化为一条简单逻辑线：

> **如 X 适用 → Y 执行 Z → 通过路径 R。**

已发布文字不需要使用这种机械形式。定稿前，用它找出隐藏的行动者、条件、接收者或路径。

对实质重组的段落，例如把段落拆成项目符号、分开条件、重排路径，或把密集句子拆开，应在审核证据中记录简短的 **逻辑线**。该逻辑线应显示修订后的呈现方式保留原有条件、例外、边界及必要行动。

保留意思是不可跨越的边界。不要只为缩短文字而移除治理区别、条件、例外、安全边界、权限要求或升级处理要求。

作为翻译压力测试，在英文定稿前，把已更改的面向读者段落翻成繁体中文。如 TC 版本迫使翻译者猜测行动者、条件、来源、路径、指涉对象或次序，应先修订英文。这项 TC 核对只是审核辅助；它不替换获授权的 Stage 2 翻译或合资格双语审核。

作为第二项诊断，考虑 **两名具能力的 TC 翻译者，会否可合理地从同一句英文推断出不同的行动者、接收者、条件、路径关系或范围**。如会，即使两个可能译法在语法上都自然，也应把英文视为 REVIEW_REQUIRED。应澄清英文来源，而不是在翻译阶段自行解决歧义。

如声明整个套件清晰，应审核 **每个范围内的非 README 公开页面**。抽样可支持临时审核，但不足以声明整个套件通过新读者或翻译稳健性检查。为每个范围内页面记录一项页面层级处置。

如作者或审核者曾撰写或最近编辑该页，另外进行一次 **无先入信息的新读者检查**。只判断读者可从页面实际存在的文字、结构、链接及操作点提示中理解什么。不要以记忆中的作者意图补上缺失意思。使用以下诊断问题：

> **新读者能否只从本页知道要留意什么及做什么，还是我因为已知道作者原意而自行补上了缺失意思？**

页面可依赖有明确链接的权威定义或详细方法，但必须标示这项依赖关系。不要假设读者已记住另一页内容。

作为新读者测试，在不依赖先前 BSG 知识的情况下阅读页面。一般生成式人工智能用户应能分辨：
1. 要留意什么；
2. 要决定什么；
3. 下一步做什么；以及
4. 如本页没有提供完整解决方法，应到哪里继续。

不要只按字数、相同章节长度，或风险、问题、路径、模板或支持文件数量判断本指南。

> [!important] 自定义不代表可削弱治理
> 不应只为令工作流程更容易，便移除或削弱所需的人员问责、权限界线、来源及证据要求、私隐控制、专业审核要求、升级处理条件或停止规则。

### 1.4 目前详细范围及控制架构

BSG 的主要操作次序是：

```text
识别盲点问题
→ 识别规范风险
→ 查阅控制图
→ 选择相关的已认可控制
→ 使用适用的详细指引及方法
→ 在需要责任、权限、专业知识、独立性、批准或升级处理时使用问责路径
```

不要把 **未明说的语境控制** 设为每项风险的强制第一项控制。只有在相关语境可能在任务依据中缺失、不完整或未获充分表述时，才进入其详细次序。

**未明说的语境控制** 是目前的详细控制。其最完善的实用指引涉及 **识别及安全引导提取未明说的语境**。

该控制内相关的目前任务指引涵盖查找已批准记录、检索及提取与任务相关的已批准材料、可表述性、安全转换、仅由人处理、核实、由承担责任或专门领域人士审核、停止及升级处理。不要把这些支持指引的每一部分，或可能使用类似行动的其他已认可控制，都描述为同等层级的详细模组。

使用以下受控定义：**未明说的语境** 是指在任务依据中缺失、不完整或未获充分表述的任何相关语境。任务依据包括来源资料包、提示词、实际使用的已批准材料、审核依据，以及目前任务可用的决策记录。

不要按来源位置定义未明说的语境。不要把 `context known by people` 作为规范类别。来源位置及可表述性必须保持为分开核对：

- 来源位置：人、已批准记录、两者，或不清楚；
- 可表述性：可清楚表述、可部分表述、难以表达、不安全或不适合表述，或无法完整表述以供人工智能使用。

不要暗示所有语境都可以或应该向人工智能表述。不要暗示所有可重用语境都应放入记录或检索增强生成（RAG）系统。

如重现完整路径清单，必须使用以下七项最低限度目前任务路径：

1. 只有在准确、必要、获允许、属最新及安全时，才把最低限度的已批准内容加入任务依据；
2. 只把必要影响转换为安全形式：事实或来源、限制或措辞规则、遗漏或审核指示、批准边界或由人草拟要求，或升级处理触发条件；
3. 把底层语境保持为仅由人处理，并由获授权人士指导草拟、审核、批准、时机或升级处理；
4. 根据具足够独立性的已批准来源、工具、记录或适当承担责任的审核者核实；
5. 转交承担责任或专门领域审核者；
6. 停止并升级处理；
7. 不使用亦不记录。

保留是另一项选用决定，不是第八项路径。

七项 **最低限度目前任务处理路径** 是未明说的语境控制内的处理选择。它们与 [[人工智能盲点控制图]] 中规范 **问责路径** 并非同一概念。当责任、权限、专业知识、审核、批准或升级处理需要转交另一人或流程时，目前任务处理选择可使用问责路径。

未明说语境的实用识别角度必须保留其定义，而不只是标签。来源位置及可表述性仍是分开核对。

**检索** 是把目前已批准来源找出并带入任务流程。**提取** 是从已检索来源中选出与任务相关的已批准材料。**核实** 是根据具足够独立性的已批准来源、工具、记录或适当承担责任的审核者，核对声明、来源、输出或决策依据。这些是不同操作：检索不等于提取，提取也不等于核实。

**引导提取** 是使用合适、具体而聚焦的问题或技巧，帮助一个人带出相关语境。**分类** 是评估来源位置、可表述性、可靠性、敏感度、权限、重要性及处理影响。**路径处理** 是把事项送往合适的已批准路径。**审核** 是由人按任务依据、预定用途、风险及控制作检查。

只有在所有者具备该事项所需的合适知识、权限、问责及足够独立性时，所有者确认才可支持核实。责任负责人不会自动成为独立核实者。

- 把已批准来源翻译成获授权目标语言；

- 保持本地文件名、链接、索引及导航完整；
- 批准前取得合资格双语审核。

## 7. 标题结构

### 7.1 标题层级及编号

文件标题使用一个不编号的 H1。

对非 README 的 BSG 页面，使用编号 H2 及 H3 标题。

除两份 README 外，如 H1 后不需要开场正文，第一个 H2 应立即使用 `## 1. Purpose and Scope`。该节必须先说明 **该特定文件的目的、范围及正确使用方式**。如有需要，之后可说明相关的全指南概念，但不得以 BSG 的一般说明替换该文件本身的目的。

如 H1 与紧接的第一个 H2 之间没有正文，不要在两者之间加入主题分隔线。

在非 README 文件中，把每个 H2 编号为 `1.`、`2.`、`3.`。

把每个 H3 按其所属 H2 编号为 `1.1`、`1.2`、`2.1`。

不要为 H4 编号。

H4 是一般情况下最深的标题层级。避免使用 H5。

不要由 H2 直接跳到 H4。如内容是真正的子节，使用编号 H3。对不需要导航的精简本地字段，使用粗体标签。

存储库层级及语言文件夹的 README 文件毋须为 H2 及 H3 编号。

如两个章节执行相同功能，使用已批准的标题。只有当功能确实不同时，才使用不同标题。

不同文件的章节如有相同用途，应使用相同的已发布标题名称。不要只为文字变化而加入同义词。

`目的及范围` 章节必须回答 **本文件** 用来做什么、何时使用，以及它不尝试替换什么。如相关，可在之后加入全指南目的或人工智能限制背景，但这些内容不得成为该节唯一内容。

### 7.3 标题与粗体标签

如内容构成真正的章节或子章节，应使用标题。

在 H3 之下，如读者可能需要进行以下工作，应使用不编号的 H4：

- 通过导航或目录找到内容；
- 直接链接到内容；
- 分开审核或维护内容；
- 把它与平行规则或流程阶段区分；
- 阅读其下的多个段落、重要清单或表格，或独立程序。

如内容只是当前章节中简短的本地部分，应使用粗体标签，例如：

- 短字段或类别；
- 例子；
- `Use` 或 `Avoid` 标签；
- 检查清单组别；
- 报告组别；
- 引入一段文字或清单的简短标签；
- 不需要独立导航的作者行动、审核检查或证据标签。

使用以下实用测试：

```text
读者是否可能合理地要求直接前往这部分？
→ 使用标题

这是否只引出当前章节中的简短部分？
→ 使用粗体标签
```

标题通常引出具有本身目的的内容。粗体标签通常引出仍属于当前标题目的的内容。

不能单靠长度决定结构。含有数个段落、实质清单或表格、独立规则或流程阶段，或可独立维护指引的粗体标签区块，通常应改为 H4。

如内容实际上构成真正的子章节，不要只为避免使用 H4 而使用粗体标签。

如只需要视觉强调，而简短粗体标签已足够，不要使用 H4。

在相同结构层级执行相同功能的项目应使用相同处理方式。除非功能确实不同，否则不要在平行项目中混用标题及粗体标签。

### 7.4 重复条目集合

把重复条目置于一个编号集合标题下，例如 `风险`、`控制`、`方法`、`问责路径`、`审核者决定`、`检查清单项目`、`问题`、`模板` 或 `风险类别`。

每个具名条目使用已编号 H3，条目的标准章节使用不编号 H4。

为同等条目使用稳定结构。没有原因时，不要让同等条目逐渐变成不同结构。

## 8. 条目结构标准

### 8.1 目的

「条目结构标准」告诉读者及编辑，每个重复条目应包含什么、哪些部分是必须、哪些部分是可选，以及哪些简短字段应保留为粗体键值对。

---

### 8.2 必备章节

每个新条目均须包括所有必备章节。不要留下空白的必备标题。

---

### 8.3 选用章节

只有在包含有用内容时才加入选用章节。不要只为令条目外观相同而加入空白标题。

如条目结构标准用来说明选用子节的意思，应以 H4 标题及解释段落逐一界定。项目符号清单可摘要可用子节名称，但不得替换定义。

---

### 8.4 文件专用标准

#### 现有集合

遵循相关文件中的条目结构标准。风险条目、控制图风险关联条目、审核卡项目、术语表条目、引导提取问题、模板字段、审核者适任性核对及决策标签的功能并不相同，所需必备章节亦可能不同。

除非所有者批准结构变更，否则保留现有的重复条目模式。

对 [[人工智能盲点控制图]]：

- 保留一个 `登记表条目结构标准`，管辖 `控制`、`方法` 及 `问责路径` 中的重复条目；
- 在 `控制` 登记表定义每项规范控制；规范名称以 `Control` 结尾；
- 要求每项控制条目说明其定义、控制目标、边界、指引可用情况，以及有实际意义时的相关规范方法；对每项相关方法，应简要解释 **它如何帮助执行或支持该控制**，而不是只列名称；
- 在 `方法` 登记表定义每项规范方法；规范名称以 `Method` 结尾；
- 要求每项方法条目说明其定义、目的、所支持控制、需要时的适用条件、边界，以及详细指引位置或可用情况；对每项所支持控制或明确相关的控制组别，简要解释 **该方法提供什么作用**，而不是只列名称；
- 在 `问责路径` 登记表定义每项规范问责路径；规范名称以 `Route` 结尾；
- 要求每项问责路径条目说明其定义、适用条件、问责归属、责任／权限／专业知识功能，以及边界；
- 不要只为视觉对称而机械式加入空白登记表字段；真正例外需要所有者批准的理由；
- 使用独立的 `风险关联条目结构标准` 管辖风险关联条目；
- 每项规范风险使用一个风险关联条目，并保留风险库的精确风险名称；
- 说明 **为何** 每项具名控制、方法或问责路径与该风险相关，而不是呈现没有解释的扁平清单；
- 令风险关联章节可由控制图的目的及范围直接到达，让读者不需要先读完规范登记表才可使用控制图；
- 区分最直接处理该风险的控制，与只在已说明条件下适用的其他控制；
- 把方法呈现为执行或支持相关控制的方式，而不是与选择控制并列的同等替代项；
- 把问责路径呈现为在责任、权限、专业知识、审核、批准或升级处理需要转交其他地方时使用的路径；
- 令风险库集中于风险意思及审核者行动；不要在每项风险库条目重复完整的风险到控制／方法／路径关联清单；
- 在相关时包括未明说的语境控制，而不是把它当作看不见的默认；
- 不要只为完成关联条目而虚构控制、方法或问责路径；
- 不要暗示已列项目目前不存在、尚未应用或必定另行需要；
- 不要让目前详细范围决定长期控制架构；
- 在面向读者的操作流程中，风险 → 控制选择必须先于任何控制专用方法。

对 [[人工智能盲点风险库]]：

- 保持该页为唯一规范风险定义登记表；
- 每项风险集中说明风险是什么、如何出现、未明说的语境可能如何影响、负责人必须解决什么，以及审核者行动；
- **不要** 在每项风险条目内重复完整的 `相关控制、方法及问责路径` 字段；
- 依靠页面层面的目的及范围把读者导向控制图，而不是在每项风险后加入同一导航句；以及
- `其他实施备注` 保持为选用，而不是例行章节：只有在它加入否则会丢失的独特风险专用实用经验时才保留；
- 不要把 `其他实施备注` 用作相关控制、方法、问责路径、审核者、负责人、文件或流程的杂项清单；关联映射由控制图负责；
- 如保留实施备注，说明 **为何重要** 及 **读者应做什么**；如项目符号有助扫读便使用；以及
- 如核心风险章节或另一权威页面已包含相同意思，整个章节应移除。

对首次使用及未明说语境页面：

- 令 [[由此开始]] 集中教授简短首次使用路径及新读者应记住的少数概念；如完整受保护七项处理路径的操作细节已存在于 [[人工智能盲点审核卡]] 及 [[未明说的语境控制]]，不要在这里再完整复制；
- 保持 [[人工智能盲点审核卡]] 为精简目前任务工作辅助；如读者在行动点需要，操作检查清单可在该处重复；
- 保持 [[未明说的语境控制]] 为未明说语境识别及处理次序的详细权威；不要在其中复制规范风险到控制关联图；
- 保持 [[机构情境处理]] 为简短导航及工作例子桥梁；不要在其中复制完整七项处理路径、完整保留准则或另一套详细控制程序；以及
- 令 [[术语表]] 条目集中于术语意思及区别。如指引页面已拥有详细识别分类或操作程序，不要在术语表重复；以及
- 术语表例子保持概念性。例子可命名规范项目来说明概念，但不得列举由 [[人工智能盲点控制图]] 拥有的风险到控制、控制到方法、方法到控制或其他规范关联集合。

#### 新集合

建立新的重复条目集合时，界定：

- 条目名称及目的；
- 必备字段或章节；
- 选用字段或章节；
- 链接或依赖；
- 审核要求；
- 维护要求。

## 14. Markdown 及 GitHub 格式规则

### 14.1 原始 Markdown 审核

检查原始文件内容，不要只依赖呈现预览。

审核行尾空格、硬换行、换行符、缩排、结构标记、代码区块、前置资料、链接、表格及技术字面内容。

---

### 14.2 分节线及空白行

此惯例只适用于非 README Markdown 文件。存储库层级及语言文件夹的 `README.md` 文件明确豁免。

在两个标题层级套用紧接子标题例外：

- 当 H1 与紧接的首个 H2 之间没有正文内容时，不要在两者之间加入主题分隔线；
- 当 H2 与紧接的首个 H3 之间没有正文内容时，不要在两者之间加入主题分隔线。

如父层标题与子层标题之间有正文内容，只在子层标题前加入一条主题分隔线。

其后每个 H2 前都必须刚好有一条主题分隔线，不论前面是 H2、H3、H4、段落、清单、表格、提示框、代码区块或其他正文内容。

其后每个 H3 如在正文内容之后开始，或紧接另一个 H3 或 H4，其前都必须刚好有一条主题分隔线。

正文内容包括段落、清单、表格、提示框、引用区块、围栏式代码、图片、内容链接及其他面向读者的材料。空白行、主题分隔线本身及完整 HTML 注解不算正文内容。

每条主题分隔线前后都使用刚好一个空白行。此规则适用于 **每一条有效的主题分隔线**，包括页末／页脚分隔线及紧接围栏式代码后的分隔线，而不只是标题前的分隔线。不要连续使用主题分隔线，也不要在主题分隔线周围加入多个空白行。

标题与其后内容之间使用一个空白行。不要在 H4 标题前加入主题分隔线。

**应使用**

```md
# 文件标题

## 1. 紧接的第一个主要章节
```

```md
## 2. 主要章节

### 2.1 紧接的第一个小节
```

```md
## 3. 主要章节

简介文字。

---

### 3.1 新小节
```

**应避免**

```md
# 文件标题

---

## 1. 紧接的第一个主要章节
```

```md
## 2. 主要章节

---

### 2.1 紧接的第一个小节
```

---

### 14.3 GitHub 强制换行

GitHub 一般会把同一段落内连续的实体行合并。只有在有意要求分开显示时，才使用两个行尾 ASCII 空格。

常见情况包括联系资料、签名行、反馈标签及链接、成对的简短指引行，以及页脚署名。

不同语言不需要强制换行完全一致。按每个文件的预定呈现方式判断。

**如两行必须在画面上分开，使用强制换行**

```md
Win.Win@Skybroad | winwin.skybroad@gmail.com  
版本 1.0 | 根据知识共享署名 4.0 国际许可协议（CC BY 4.0）— 可自由分享及改编，需署名 Win.Win@Skybroad
```

如正常段落换行已足够，不要使用行尾空格。

---

### 14.4 表格

表格标题应简短并具描述性。

重新格式化时保留每一行的意思。检查直线符号、强调、链接及换行能否正确呈现。

如果正文或检查清单更清晰，不要强迫把每个概念放入表格。

---

### 14.5 编码及换行格式

使用不含字节顺序标记（BOM）的 8 位元 Unicode 转换格式（UTF-8），使用换行字符（LF）作为行尾，并在文件结尾只保留一个最后换行。报告混合或非预期的行尾格式。

不要更改未变更文件的行尾、空白、换行方式或表格间距。

### 16.8 法律、法规、私隐及专业语气审核

对法律、法规、隐私、财务、雇佣、安全保护、医疗、心理、辅导、牧养、神学、技术、平台及其他专门领域内容进行针对性语气审核。

#### 搜索什么

搜索表示确定性的词语，包括：

`always`、`every`、`never`、`cannot`、`only`、`automatically`、`constitutes`、`required by law`、`compliant`、`illegal`、`defaults to`、`will reject`、`will require` 及 `no recall`。

一个匹配项目只是 **审核候选项目**，不是自动失败。

亦搜索审核周期内变更的每个规范术语、风险名称、法律或隐私表述、控制陈述、后果解释、权限边界或专门领域资格措辞。

#### 如何评估每个结果

对每个匹配项目，判断该陈述是否：

- 是稳定概念或强制治理边界；
- 取决于句子未述明的事实；
- 取决于现行法律、法规指引、平台功能、模型行为或机构安排；
- 暗示最终专门领域结论；
- 暗示确定的外部决定或后果；
- 应改用有条件、以来源为本的措辞；
- 需要当前权威来源、核对日期或合资格审核。

#### 文字变更后

确认：

- 风险库、控制图、审核卡、术语表、指引、模板、README、导航或翻译备注中没有遗留过时措辞；
- 工作卡及模板所教导的风险及控制模型与其来源指引一致；
- 任何重新命名的风险、控制、方法或问责路径仍可追溯至其规范意思及目前控制架构。

### 16.11 BSG 模型、风险、路径及适任性审核

在整个套件确认：

- 所有者目的下的读者结果仍然清楚：一般生成式人工智能用户不需要先阅读术语表，也能识别人工智能盲点概念、理解相关风险的意思，并找到至少一条缓解路径；
- 预期读者反覆识别的术语使用一个稳定的受控英文形式，并在 Stage 2 前识别固定目标语言映射覆盖；
- 每项规范风险都支持三个所有者目的问题：可能出什么问题、为何重要，以及下一步做什么；
- 如未提供详细缓解措施，风险至少指出相关控制、方法、问责路径或其他已批准下一步；
- 首次使用旅程支持「**这可能是人工智能盲点**」这个备用识别，以及返回 Win.Win 人工智能盲点指南取得进一步指引的路径；
- 人工智能盲点仍然比未明说语境更广；
- 已批准的目前详细重点句子仍然准确；
- 任务依据的意思获保留；
- 来源位置、可表述性及可靠性仍然彼此不同；
- 人员、已批准记录、两者或不清楚仍是来源位置选项；
- 受控的可表述性类别保持完整；
- 如重现完整七条最低限度目前任务路径，次序仍按已批准次序；
- 保留仍是独立的受治理决定；
- 检索、提取、引导提取、分类、路径处理、审核及核实仍彼此不同；
- 所有者确认不会自动构成独立核实；
- 角色、适任性、能力、许可、独立性及权限仍彼此不同；
- 规范风险名称及决策标签保持精确；
- 问题优先的风险架构保留风险专用的提示词层面、审核者、仅由人处理、安全转换及升级处理控制；
- 受保护例子、问题、触发条件、字段及可重用习惯仍可分开识别；
- 风险识别先引向控制选择，再引向控制专用方法；
- 未明说的语境控制没有被呈现为所有风险的通用第一个控制；
- 控制、方法及问责路径保持不同，而每个规范名称只对应控制图中的一个登记表；
- 术语表界定架构概念，但不重复个别规范登记表的完整定义；
- 控制图同时包含登记表条目结构标准及独立的风险关联条目结构标准；
- 每项规范风险在控制图有一个风险关联条目，解释为何所列控制、方法及问责路径可能相关；
- 控制图区分最直接相关的控制与其他有条件控制，并且不把控制、方法及问责路径呈现为没有区别的一张清单；
- 风险库风险条目不重复完整关联图；
- 未明说的语境控制不重现由控制图拥有的规范风险→控制关联图；
- 由此开始教授简短首次使用路径，而不重现完整详细的七路径处理次序；
- 审核卡以先扫描格式呈现风险识别提示，并可保留审核期间需要的操作点检查清单；
- 机构情境处理维持短篇导向，而不是第二套详细未明说语境程序；
- 术语表条目界定及区分术语，但不重现由其他页面负责的冗长详细识别分类或操作程序；
- 套件整体的重复内容用来强化短记忆提示或操作点安全，而不是反覆教导冗长查阅材料；
- 目前详细范围措辞把未明说的语境控制识别为目前详细控制，同时保留「识别及安全引导提取未明说语境」作为最深入的实务处理；
- 检索、提取及核实仍彼此不同，包括在任何结合检索及提取的方法内；
- 未经所有者批准架构，不加入推测性的更高层控制分组。

### 16.12 发现严重程度

`P1` 及 `P2` 是受控的发现严重程度标签。它们不是 Purpose、Permission 或 Proof 的缩写。

**P1** 用于已确认会影响意思、权限、批准、问责、私隐、法律或专业边界、发布身份、必要链接、Markdown 呈现或风险处理的问题。

如已确认问题涉及术语、结构、英式英语拼法、清单标点、连接词、发布格式、共用样板文字、必备强制换行、标题、表格、导航、release、版本、frontmatter 或中文发布惯例，但不会改变核心治理意思，使用 **P2**。

如证据、配对、来源权威、专门领域术语、翻译意思、审核者适任性、所有者意图或预定呈现仍不确定，使用 **仅供审核**。

### 16.13 整体状态

只有在没有任何可执行发现，而且获授权执行边界内所有必备确定性及语义检查均已完成时，才使用 **PASS**。

当没有已确认的修正阻碍，但仍有所有者、双语、专门领域、机构、代表性读者、配对、术语、release 或发布决定未解决时，使用 **REVIEW REQUIRED**。

当已确认的可执行问题仍存在，或必备输入、提取、解码、结构、术语、字体、链接、身份、release、版本或 P1 呈现问题妨碍可靠完成时，使用 **FAIL**。

#### 翻译就绪关卡

不要把整洁的验证器结果、作者自我审核或所有者略读本身视为英文套件已可进入 Stage 2 翻译的证明。在所有者宣告英文套件 **TRANSLATION READY** 前，对该确切套件要求以下所有项目：

1. 没有未解决 P1 或 P2 发现；
2. 对每个范围内非 README 公开页面完成逐页新读者及 TC 翻译压力测试；
3. 至少一次审核者中立的独立审核，判断套件是否符合所有者目的接受准则，并明确说明任何抽样限制；
4. 所有可执行语义发现均已修正，或由所有者明确接受为不变更决定；
5. 受治理术语覆盖已与所有者指定外部术语权威核对，没有未解决受控术语缺口；
6. 作者及编辑指南、审核工具包、验证器、翻译备注及跨文件导航均已按最终英文内容重新评估；
7. 最终套件、权威、工具及证据身份按内容哈希／版本记录，而不是只依赖上载外层文件名；及
8. 所有者明确宣告这个确切英文套件为 **TRANSLATION READY**，并指定为冻结 Stage 2 来源基准。

该宣告后任何英文来源变更都会重新打开 Stage 1，并需要新的 Stage 2 基准替换原基准，而不是在翻译阶段静默修正。

## 17. 维护及变更控制

### 17.1 共用规则

把共通的编辑、结构、本地化、验证、版本、打包、发布、证据及报告规则集中保留在本文件，不要在每个公开文件重复。

对所有者确认的每项差异，评估现有控制为何会容许问题出现。在实际可行时，加入或加强预防性的撰写规则、审核规则、验证器检查、测试或控制组合。不要只修正目前文件便结束一类会重复发生的差异。

对 **每项修正或完整套件变更**，明确重新评估本作者及编辑指南、目前审核工具包及目前验证器是否需要相应更新。如现有控制已覆盖问题，记录 `no change required`；不要只为制造版本变动而更新元件。

### 17.2 文件专用规则

只有当个别文件有特定依赖关系时，才保留 `Maintenance and Change Control` 章节，例如稳定的链接条目名称、其他地方采用的规范措辞、风险库与控制图对齐、审核卡同步、模板字段对齐、受保护例子或审核者适任性控制。

---

### 17.3 相关参考文件

只有当原有或获批准内容具有真实而有用的跨文件关系时，才加入「相关参考文件」。不要只为对称而加入空白或推测性章节。

不要把领英系列、文章、培训课程、未发布说明、演示文稿或其他外部评论，变成理解或安全使用本指南的先决条件。外部材料可以介绍、说明、解释或推广本指南，但每项必须指示、控制、边界、路线及停止条件都必须保留在已批准公开套件内。

撰写重要定义、控制、例子、边界、角色、风险、路径、决定及指示时，确保它们在目前发布之后仍然有用。

不要把长期适用的指引写成临时发布说明、未来承诺或未发布计划。

不要说另一份指南、语言版本、快速版、培训资源或支持文件已存在，除非它已获批准、发布及链接。如所有者批准提及未来工作，清楚说明它尚未提供，而且理解或安全使用本指南并不依赖该未来工作。

### 17.4 审核周期

### 17.5 Frontmatter

除非获授权进行受控迁移，否则保留既定 frontmatter 字段及次序。

常见字段包括：

- `title`；
- `created`；
- `updated`；
- `version`；
- `tags`；
- `status`；
- `type`；
- `source-role`；
- `locale`；
- `licence`。

保持 `created` 不变。

每份已修改的公开文件都必须包含 `updated` 字段，并把它设为所有者批准的修正日期。如该字段不存在，应予以新增。

不要更改其他内容不变文件的 `updated` 字段。未修改的文件必须保持字节完全相同。

只为更新 `updated` 而变更文件属于缺陷。

Frontmatter 标签及简短标签式元数据值不需要以句号结尾。不要只为视觉一致而加入标点。

### 17.6 文件版本

文件版本属于一个公开文件。

首次发布前：

- 每个现有公开文件维持版本 `1.0`；
- 发布前的编辑、结构、翻译、排版、证据、验证或打包修正，不要递增版本；
- 只有所有者明确开始新的已发布文件版本时才更改版本。

发布后：

- 只变更所有者批准版本更新所包括的文件；
- 未变更文件维持现有版本；
- 每个页脚版本与 frontmatter 版本完全一致。

使用所有者就该作品及语言批准的标准页脚。

对目前 BSG 套件，每个非 README 公开 Markdown 文件都必须使用已批准的短标准页脚。`README.md` 是已有文件角色规则的例外，因为它使用自己的已批准导航、联系、存储库路径及授权条款页脚结构。不要只为视觉对称而把短标准页脚加入 README。

在 `en_HK` 中，使用已批准、包含 `CC BY 4.0` 的简短英文授权条款措辞。

在已发布的 `tc_HK` 及 `sc_HK` 版本中，于相应页脚使用完整已批准的繁体中文或简体中文授权条款名称，后接 `（CC BY 4.0）`。

授权条款措辞可遵循已批准的 Win.Win 共用模式，但版本号必须始终与目前 BSG 文件本身的 frontmatter 版本相符。不要从其他成品、语言文件、套件或例子复制版本号。

把已批准页脚措辞视为受控共用样板文字。除非所有者明确批准新的页脚模式，否则不要缩短、扩展、重新翻译或以其他方式改动。

文件版本与套件发布版本分开。

### 17.7 套件发布及发布历史

套件发布是完整作品的已发布快照。

首次发布前，除非所有者明确更改，套件发布版本维持 `1.0`。

发布版本号显示于适用 README 文件。

发布后，一个 release 可包含不同文件版本的文件。

记录对读者有实质影响的发布变更，例如：

- 新公开文件；
- 实质的风险、控制、路径、决定、权限或批准变更；
- 新语言文件夹；
- 实质套件重组；
- 重要的范围、受众或公开语言变更；
- 实质新增的维护或调整能力。

除非所有者要求，细微排版、标点、自我指称、证据、验证或打包修正不需要加入 release 历史备注。

---

### 17.8 索引及导航维护

新增、重新命名、移除或实质改变公开文件用途时：

- 更新适用语言文件夹的 README 索引；
- 更新相关导航文件及读者路径；
- 每个 wikilink 使用确切本地文件名；
- 如已有翻译，保留既有本地化命名模式；
- 说明文件帮助读者理解或做什么，而不只是说明其文件类型；
- 验证每个新本地链接。

审核根目录 `README.md` 是否受依赖影响，并把任何问题报告给所有者。BSG 作者不得修改它。

如 `en_HK/README.md` 在其他方面属工作范围，仍须精确保留其受保护 Master Source 提示框。导航、语言文件夹、元数据或发布变更均不得改动该提示框。

### 17.9 公开套件与证据分离

公开压缩档只能在 `public/` 包装文件夹下包含预定公开文件。

不要在公开压缩档内放置：

- 外部 `file_list.txt` 或同等文件清单；
- 校验和或哈希清单；
- 审核报告；
- 验证输出；
- 变更登记表；
- 比较矩阵；
- 修正提示词；
- 工具源代码或测试；
- 证据文件；
- 暂存文件。

对 BSG 套件及变更控制，使用直接 ZIP 清单，以及直接来源→最终路径和字节比较。

所有证据均放在公开套件之外。

### 18.3 完整套件产生的标准输出

当 ChatGPT 辅助作者产生完整后续 BSG 套件时，除非所有者明确缩窄交付范围，否则提供以下标准输出：

1. 修订后的公开 BSG 套件 ZIP；
2. 目前独立 **作者及编辑指南**；
3. 目前 **审核工具包**；
4. 目前 **Stage 1 验证器**；
5. 验证证据，包括最终验证器摘要及回归测试结果；
6. 清晰度范围的逐页新读者及 TC 翻译压力测试审核证据；
7. 变更文件登记表或同等精确变更报告，包括 **工具控制重新评估**，记录作者及编辑指南、审核工具包及验证器是否已修订，或为何不需要变更；
8. 根据最终确切差异创建的 **GitHub 提交消息 Markdown 文件**，说明变更内容及原因；
9. 一份 **独立人工智能审核演示文稿 Markdown 文件**，供另一个人工智能审核者使用，而不需要依赖作者记忆中的意图；及
10. 一个包含目前可下载交付成果的集成 ZIP。

如所有者指定术语权威是套件的治理输入，在证据及集成交付成果中识别它，而不要静默修改。

GitHub 提交消息必须描述实际最终变更范围，而不是较早草稿或预定变更清单。包括变更的主要原因，并在重要时指出理解差异所需的关键保留边界。

独立人工智能审核演示文稿必须保持审核者中立。不要假定特定审核者名称。它应识别确切套件及基准、摘要变更内容及原因、列明所有者目的接受准则、把审核集中于具体缺陷或有价值的理解改进、在适用时要求意思保留及 TC 翻译压力测试，并避免没有明确读者或治理好处的广泛风格重写。
