# 作者及編輯指南

## 1. 目的及範圍

當您為 Win.Win 人工智能盲點指南進行 **撰寫、編輯、自訂、本地化、審核、驗證、發布或維護** 時，請使用本頁。它是套件層面的撰寫權威，涵蓋結構、術語、控制強度、文件角色、交叉參照、本地化、驗證、維護及變更報告。

在本作者及編輯指南中，**Win.Win 人工智能盲點指南（BSG）** 及 **Win.Win 人工智能應用案例指南（UCG）** 在此定義後可分別縮寫為 **BSG** 及 **UCG**。BSG 及 UCG 只供撰寫、維護、審核、驗證及證據工作使用。不要假設面向讀者的檔案已定義或應使用其中任何一個縮寫。

本指南適用於 Win.Win 維護者、調整 BSG 的機構、作者及編輯、審核者及專門領域人士、翻譯者及雙語審核者，以及支援受控工作的人工智能助理。

其範圍是本指南內容的管治及維護。它不取代 [[如何使用本指南]] 中面向讀者的操作指引、[[指南範圍及定位]] 中的範圍聲明、[[詞彙表]] 中的規範術語，或本指南可能要求讀者使用的任務層面專門領域流程。

BSG 的指定受眾是個人、教會、非牟利機構，以及中小企業。其他讀者可按其情境調整本指南，但不得削弱強制控制。

### 1.1 目的忠實度及讀者結果

Win.Win 人工智能盲點指南協助讀者識別這類情況：人工智能輔助輸出可能看起來清楚、完整、平衡或有信心，但人工智能無法可靠地看見、保留、判斷、核實、授權，或為負責人必須處理的事項承擔責任。

人工智能盲點比未明說的語境更廣。本指南的廣泛模型包括任務依據差距，以及涉及真實或本地理解、判斷、權限、問責、獨立核實、受眾影響、專業直覺、營運記憶、後果意識，或其他人工智能無法可靠掌握事項的更廣界線。

Win.Win 人工智能盲點指南目前的詳細重點是識別及引導提取未明說的語境。

關於檢索及擷取已批准來源、可表述性、安全轉換、僅由人處理、核實、由承擔責任或專門領域人士審核、停止及升級處理的支援指引，可協助讀者在識別或帶出情境後採取行動。不要把這些支援指引描述為同等層級的詳細模組。

本指南把引導提取、檢索、擷取、安全處理、審核、核實、路徑處理、停止、升級處理及選用保留視為彼此相關但 **在架構上不同的功能**。視乎情境，一個項目可能是規範控制、規範方法、控制內的行動、處理決定、審核活動、問責路徑、升級處理行動或保留決定。不要把每項降低風險的活動都稱為控制。一個廣泛問題、一份完整來源資料包或一個詳細提示詞，都不能取代權限、獨立核實、合資格判斷、承擔責任的審核、升級處理或停止規則。

審核 BSG 是否達成其目的時，請檢查讀者能否：
- 識別相關盲點；
- 找出負責人必須解決的問題；
- 在適當時尋找或引導提取合適語境；
- 為目前任務選擇安全路徑；
- 讓具合適適任性的審核者參與；以及
- 在問題無法安全解決時停止或升級處理。

> [!important] 擁有人目的及預期讀者結果
> 面向讀者的 BSG 內容，是為大約 20–80 歲的一般成人設計；他們熟悉使用生成式人工智能（GenAI），但未必熟悉人工智能管治術語，亦可能傾向信任流暢、精緻或有信心的人工智能輸出。
>
> 設計本指南時，應令讀者在使用後更有可能記住 **人工智能盲點** 的核心概念、識別重要的人工智能盲點風險模式，並記住至少一項相關緩解路徑，例如控制、方法、問責路徑或詳細指引。如果讀者日後記不起確切風險名稱或解決方法，最低限度的預期結果是他們能識別 **「這可能是人工智能盲點」**，並知道 **Win.Win 人工智能盲點指南** 是可返回查閱更多資料及實用緩解指引的地方。

撰寫或審核面向讀者的內容時，使用以下擁有人目的驗收準則：

1. **術語一致性** — 同一概念使用一個穩定的受控名稱，讓讀者日後能再次識別。簡單易明的導覽可解釋受控術語，但不得建立競爭名稱。
2. **一般成人可理解程度** — 一般 GenAI 使用者應可在毋須先研讀詞彙表的情況下，理解關鍵訊息及下一步行動。如有需要，在首次使用不熟悉的受控術語時，加入簡短的即場解釋。
3. **意識加緩解** — 每項規範人工智能盲點風險都必須協助讀者理解可能出現甚麼問題、為何重要，以及下一步應做甚麼。如未提供詳細緩解指引，至少指出一項相關控制、方法、問責路徑或其他已批准的繼續路徑。

把讀者識別及記憶視為設計目標，而不是保證。不要聲稱本指南可確保讀者會記住甚麼。

#### 新讀者清晰度及翻譯穩健性

對每份非 README 的面向讀者頁面，保留原有實質意圖，但呈現方式應讓新讀者毋須拆解複雜英文句式，也能理解應採取的行動。

使用以下預設做法：
- 如可能不清楚由誰行動，明確指出行動者；
- 條件使用 **if** 或 **when**；**where** 主要保留給位置，或明確的地方／來源問題；
- 除非被詢問的人或系統已清楚指明，否則不要單獨使用 `Ask:`、`ask what`、`ask whether` 或類似文字；
- 行動指示以清楚動詞開始，例如 **identify、check、consult、retrieve、verify、route、decide、stop** 或 **record**；
- 如由人掌握的語境、紀錄中的語境、人工智能處理及僅由人處理使用不同路徑，請分開說明；
- 如項目符號能減低認知負荷，對平行選項、準則、路徑或後果使用項目符號；
- 如次序重要，使用編號步驟；
- 如以段落能更清楚表達概念之間的關係，保留段落形式；
- 如分組代表有意義的關係、選擇決定或實施選項，不要使用沒有解釋的純名稱清單；應簡要說明 **為何每項相關、何時適用或它擔當甚麼角色**；
- 如只是庫存清單、索引、導覽輔助，或其他毋須解釋項目關係的情況，純清單仍可接受；
- 在可行情況下，每句優先表達一項主要行動或判斷；以及
- 如指涉對象可能有多於一種理解，避免使用 **this、it、they** 或 **that** 等含糊代名詞。

**行動者－行動－對象／接收者－條件－路徑原則**

對每項指示、決策規則、審核提示或路徑陳述，文字本身必須足以還原其操作邏輯。在相關時，新讀者應能識別：

- **行動者** — 誰採取行動；
- **行動** — 他們做甚麼；
- **對象或接收者** — 他們對甚麼或誰採取行動、核對、諮詢、提問、核實、轉交或審核；
- **條件** — 行動在何時或甚麼情況下適用；以及
- **路徑** — 事項是透過人工智能、人、已批准紀錄、僅由人處理、核實、承擔責任的審核或升級處理。

不要依賴作者記憶中的意圖去補足其中任何元素。已發布文字毋須使用上述標籤，但讀者必須能在毋須猜測的情況下還原邏輯。

不要把概念、控制、方法或問責路徑擬人化，好像它本身就是執行審核行動的人。避免使用 `Reviewer standing asks whether...`、`Materiality asks what...` 或 `Source location asks where...` 等文字。優先使用以下形式之一：

- 直接陳述概念，例如 `Reviewer standing concerns whether...`；
- 陳述審核者行動，例如 `Check whether...`；或
- 明確標示診斷問題，例如 `Use this question: ...`。

使用 **ask** 時，如情境尚未令雙方清楚無疑，應同時寫清楚：**誰提問 + 向誰或甚麼提問 + 希望取得甚麼資料**。僅因作者知道預期提問者是誰，並不足以令 `Ask what...` 或 `ask whether...` 變得清楚。

作為審核診斷，如有幫助，可把每項實質指示簡化為一條簡單邏輯線：

> **如 X 適用 → Y 執行 Z → 透過路徑 R。**

已發布文字毋須使用這種機械形式。定稿前，用它找出隱藏的行動者、條件、接收者或路徑。

對實質重組的段落，例如把段落拆成項目符號、分開條件、重排路徑，或把密集句子拆開，應在審核證據中記錄簡短的 **邏輯線**。該邏輯線應顯示修訂後的呈現方式保留原有條件、例外、界線及必要行動。

保留意思是不可跨越的界線。不要只為縮短文字而移除管治區別、條件、例外、安全界線、權限要求或升級處理要求。

作為翻譯壓力測試，在英文定稿前，把已更改的面向讀者段落翻成繁體中文。如 TC 版本迫使翻譯者猜測行動者、條件、來源、路徑、指涉對象或次序，應先修訂英文。這項 TC 核對只是審核輔助；它不取代獲授權的 Stage 2 翻譯或合資格雙語審核。

作為第二項診斷，考慮 **兩名具能力的 TC 翻譯者，會否可合理地從同一句英文推斷出不同的行動者、接收者、條件、路徑關係或範圍**。如會，即使兩個可能譯法在文法上都自然，也應把英文視為 REVIEW_REQUIRED。應澄清英文來源，而不是在翻譯階段自行解決歧義。

如聲稱整個套件清晰，應審核 **每個範圍內的非 README 公開頁面**。抽樣可支援臨時審核，但不足以聲稱整個套件通過新讀者或翻譯穩健性檢查。為每個範圍內頁面記錄一項頁面層級處置。

如作者或審核者曾撰寫或最近編輯該頁，另外進行一次 **無先入資訊的新讀者檢查**。只判斷讀者可從頁面實際存在的文字、結構、連結及操作點提示中理解甚麼。不要以記憶中的作者意圖補上缺失意思。使用以下診斷問題：

> **新讀者能否只從本頁知道要留意甚麼及做甚麼，還是我因為已知道作者原意而自行補上了缺失意思？**

頁面可依賴有明確連結的權威定義或詳細方法，但必須標示這項相依關係。不要假設讀者已記住另一頁內容。

作為新讀者測試，在不依賴先前 BSG 知識的情況下閱讀頁面。一般生成式人工智能使用者應能分辨：
1. 要留意甚麼；
2. 要決定甚麼；
3. 下一步做甚麼；以及
4. 如本頁沒有提供完整解決方法，應到哪裏繼續。

不要只按字數、相同章節長度，或風險、問題、路徑、範本或支援檔案數量判斷本指南。

> [!important] 自訂不代表可削弱管治
> 不應只為令工作流程更容易，便移除或削弱所需的人員問責、權限界線、來源及證據要求、私隱控制、專業審核要求、升級處理條件或停止規則。

### 1.4 目前詳細範圍及控制架構

BSG 的主要操作次序是：

```text
識別盲點問題
→ 識別規範風險
→ 查閱控制圖
→ 選擇相關的已認可控制
→ 使用適用的詳細指引及方法
→ 在需要責任、權限、專業知識、獨立性、批准或升級處理時使用問責路徑
```

不要把 **未明說的語境控制** 設為每項風險的強制第一項控制。只有在相關語境可能在任務依據中缺失、不完整或未獲充分表述時，才進入其詳細次序。

**未明說的語境控制** 是目前的詳細控制。其最完善的實用指引涉及 **識別及安全引導提取未明說的語境**。

該控制內相關的目前任務指引涵蓋尋找已批准紀錄、檢索及擷取與任務相關的已批准材料、可表述性、安全轉換、僅由人處理、核實、由承擔責任或專門領域人士審核、停止及升級處理。不要把這些支援指引的每一部分，或可能使用類似行動的其他已認可控制，都描述為同等層級的詳細模組。

使用以下受控定義：**未明說的語境** 是指在任務依據中缺失、不完整或未獲充分表述的任何相關語境。任務依據包括來源資料包、提示詞、實際使用的已批准材料、審核依據，以及目前任務可用的決策紀錄。

不要按來源位置定義未明說的語境。不要把 `context known by people` 作為規範類別。來源位置及可表述性必須保持為分開核對：

- 來源位置：人、已批准紀錄、兩者，或不清楚；
- 可表述性：可清楚表述、可部分表述、難以表達、不安全或不適合表述，或無法完整表述以供人工智能使用。

不要暗示所有語境都可以或應該向人工智能表述。不要暗示所有可重用語境都應放入紀錄或檢索增強生成（RAG）系統。

如重現完整路徑清單，必須使用以下七項最低限度目前任務路徑：

1. 只有在準確、必要、獲允許、屬最新及安全時，才把最低限度的已批准內容加入任務依據；
2. 只把必要影響轉換為安全形式：事實或來源、限制或措辭規則、遺漏或審核指示、批准界線或由人草擬要求，或升級處理觸發條件；
3. 把底層語境保持為僅由人處理，並由獲授權人士指導草擬、審核、批准、時機或升級處理；
4. 根據具足夠獨立性的已批准來源、工具、紀錄或適當承擔責任的審核者核實；
5. 轉交承擔責任或專門領域審核者；
6. 停止並升級處理；
7. 不使用亦不記錄。

保留是另一項選用決定，不是第八項路徑。

七項 **最低限度目前任務處理路徑** 是未明說的語境控制內的處理選擇。它們與 [[人工智能盲點控制圖]] 中規範 **問責路徑** 並非同一概念。當責任、權限、專業知識、審核、批准或升級處理需要轉交另一人或流程時，目前任務處理選擇可使用問責路徑。

未明說語境的實用識別角度必須保留其定義，而不只是標籤。來源位置及可表述性仍是分開核對。

**檢索** 是把目前已批准來源找出並帶入任務流程。**擷取** 是從已檢索來源中選出與任務相關的已批准材料。**核實** 是根據具足夠獨立性的已批准來源、工具、紀錄或適當承擔責任的審核者，核對聲稱、來源、輸出或決策依據。這些是不同操作：檢索不等於擷取，擷取也不等於核實。

**引導提取** 是使用合適、具體而聚焦的問題或技巧，協助一個人帶出相關語境。**分類** 是評估來源位置、可表述性、可靠性、敏感度、權限、重要性及處理影響。**路徑處理** 是把事項送往合適的已批准路徑。**審核** 是由人按任務依據、預定用途、風險及控制作檢查。

只有在擁有人具備該事項所需的合適知識、權限、問責及足夠獨立性時，擁有人確認才可支援核實。責任負責人不會自動成為獨立核實者。

機構情境處理比目前詳細範圍更廣。[[人工智能盲點控制圖]] 可定義其他已認可控制，而本指南未必詳細說明。不要為超出本指南目前詳細範圍的控制，自行建立未經批准的詳細框架。

- 成品身分、目的、受眾、工作語言狀態，以及預定三語發布定位；
- 標題層級及必備章節；
- 受保護呈現及獲授權例外；
- 導覽、索引及讀者路徑；
- 重複標題及損壞錨點；
- 連結、發布資料、授權條款意思及呈現；
- 保留多語言根目錄說明時的跨語言目的對等。

### 6.2 語言資料夾及來源角色

## 7. 標題結構

### 7.1 標題層級及編號

文件標題使用一個不編號的 H1。

對非 README 的 BSG 頁面，使用編號 H2 及 H3 標題。

除兩份 README 外，如 H1 後不需要開場正文，第一個 H2 應立即使用 `## 1. Purpose and Scope`。該節必須先說明 **該特定文件的目的、範圍及正確使用方式**。如有需要，之後可說明相關的全指南概念，但不得以 BSG 的一般說明取代該文件本身的目的。

如 H1 與緊接的第一個 H2 之間沒有正文，不要在兩者之間加入主題分隔線。

在非 README 文件中，把每個 H2 編號為 `1.`、`2.`、`3.`。

把每個 H3 按其所屬 H2 編號為 `1.1`、`1.2`、`2.1`。

不要為 H4 編號。

H4 是一般情況下最深的標題層級。避免使用 H5。

不要由 H2 直接跳到 H4。如內容是真正的子節，使用編號 H3。對不需要導覽的精簡本地欄位，使用粗體標籤。

儲存庫層級及語言資料夾的 README 文件毋須為 H2 及 H3 編號。

### 7.3 標題與粗體標籤

如內容構成真正的章節或子章節，應使用標題。

在 H3 之下，如讀者可能需要進行以下工作，應使用不編號的 H4：

- 透過導覽或目錄找到內容；
- 直接連結到內容；
- 分開審核或維護內容；
- 把它與平行規則或流程階段區分；
- 閱讀其下的多個段落、重要清單或表格，或獨立程序。

如內容只是當前章節中簡短的本地部分，應使用粗體標籤，例如：

- 短欄位或類別；
- 例子；
- `Use` 或 `Avoid` 標籤；
- 核查清單組別；
- 報告組別；
- 引入一段文字或清單的簡短標籤；
- 不需要獨立導覽的作者行動、審核檢查或證據標籤。

使用以下實用測試：

```text
讀者是否可能合理地要求直接前往這部分？
→ 使用標題

這是否只引出當前章節中的簡短部分？
→ 使用粗體標籤
```

標題通常引出具有本身目的的內容。粗體標籤通常引出仍屬於當前標題目的的內容。

不能單靠長度決定結構。含有數個段落、實質清單或表格、獨立規則或流程階段，或可獨立維護指引的粗體標籤區塊，通常應改為 H4。

如內容實際上構成真正的子章節，不要只為避免使用 H4 而使用粗體標籤。

如只需要視覺強調，而簡短粗體標籤已足夠，不要使用 H4。

在相同結構層級執行相同功能的項目應使用相同處理方式。除非功能確實不同，否則不要在平行項目中混用標題及粗體標籤。

### 7.4 重複條目集合

把重複條目置於一個編號集合標題下，例如 `風險`、`控制`、`方法`、`問責路徑`、`審核者決定`、`核查清單項目`、`問題`、`範本` 或 `風險類別`。

每個具名條目使用已編號 H3，條目的標準章節使用不編號 H4。

為同等條目使用穩定結構。沒有原因時，不要讓同等條目逐漸變成不同結構。

## 8. 條目結構標準

### 8.1 目的

「條目結構標準」告訴讀者及編輯，每個重複條目應包含甚麼、哪些部分是必須、哪些部分是可選，以及哪些簡短欄位應保留為粗體鍵值對。

---

### 8.2 必備章節

每個新條目均須包括所有必備章節。不要留下空白的必備標題。

---

### 8.3 選用章節

只有在包含有用內容時才加入選用章節。不要只為令條目外觀相同而加入空白標題。

如條目結構標準用來說明選用子節的意思，應以 H4 標題及解釋段落逐一界定。項目符號清單可摘要可用子節名稱，但不得取代定義。

---

### 8.4 文件專用標準

#### 現有集合

遵循相關文件中的條目結構標準。風險條目、控制圖風險關聯條目、審核卡項目、詞彙表條目、引導提取問題、範本欄位、審核者適任性核對及決策標籤的功能並不相同，所需必備章節亦可能不同。

除非擁有人批准結構變更，否則保留現有的重複條目模式。

對 [[人工智能盲點控制圖]]：

- 保留一個 `登記表條目結構標準`，管轄 `控制`、`方法` 及 `問責路徑` 中的重複條目；
- 在 `控制` 登記表定義每項規範控制；規範名稱以 `Control` 結尾；
- 要求每項控制條目說明其定義、控制目標、界線、指引可用情況，以及有實際意義時的相關規範方法；對每項相關方法，應簡要解釋 **它如何協助執行或支援該控制**，而不是只列名稱；
- 在 `方法` 登記表定義每項規範方法；規範名稱以 `Method` 結尾；
- 要求每項方法條目說明其定義、目的、所支援控制、需要時的適用條件、界線，以及詳細指引位置或可用情況；對每項所支援控制或明確相關的控制組別，簡要解釋 **該方法提供甚麼作用**，而不是只列名稱；
- 在 `問責路徑` 登記表定義每項規範問責路徑；規範名稱以 `Route` 結尾；
- 要求每項問責路徑條目說明其定義、適用條件、問責歸屬、責任／權限／專業知識功能，以及界線；
- 不要只為視覺對稱而機械式加入空白登記表欄位；真正例外需要擁有人批准的理由；
- 使用獨立的 `風險關聯條目結構標準` 管轄風險關聯條目；
- 每項規範風險使用一個風險關聯條目，並保留風險庫的精確風險名稱；
- 說明 **為何** 每項具名控制、方法或問責路徑與該風險相關，而不是呈現沒有解釋的扁平清單；
- 令風險關聯章節可由控制圖的目的及範圍直接到達，讓讀者毋須先讀完規範登記表才可使用控制圖；
- 區分最直接處理該風險的控制，與只在已說明條件下適用的其他控制；
- 把方法呈現為執行或支援相關控制的方式，而不是與選擇控制並列的同等替代項；
- 把問責路徑呈現為在責任、權限、專業知識、審核、批准或升級處理需要轉交其他地方時使用的路徑；
- 令風險庫集中於風險意思及審核者行動；不要在每項風險庫條目重複完整的風險到控制／方法／路徑關聯清單；
- 在相關時包括未明說的語境控制，而不是把它當作看不見的預設；
- 不要只為完成關聯條目而虛構控制、方法或問責路徑；
- 不要暗示已列項目目前不存在、尚未套用或必定另行需要；
- 不要讓目前詳細範圍決定長期控制架構；
- 在面向讀者的操作流程中，風險 → 控制選擇必須先於任何控制專用方法。

對 [[人工智能盲點風險庫]]：

- 保持該頁為唯一規範風險定義登記表；
- 每項風險集中說明風險是甚麼、如何出現、未明說的語境可能如何影響、負責人必須解決甚麼，以及審核者行動；
- **不要** 在每項風險條目內重複完整的 `相關控制、方法及問責路徑` 欄位；
- 依靠頁面層面的目的及範圍把讀者導向控制圖，而不是在每項風險後加入同一導覽句；以及
- `其他實施備註` 保持為選用，而不是例行章節：只有在它加入否則會遺失的獨特風險專用實用經驗時才保留；
- 不要把 `其他實施備註` 用作相關控制、方法、問責路徑、審核者、負責人、文件或流程的雜項清單；關聯映射由控制圖負責；
- 如保留實施備註，說明 **為何重要** 及 **讀者應做甚麼**；如項目符號有助掃讀便使用；以及
- 如核心風險章節或另一權威頁面已包含相同意思，整個章節應移除。

對首次使用及未明說語境頁面：

- 令 [[由此開始]] 集中教授簡短首次使用路徑及新讀者應記住的少數概念；如完整受保護七項處理路徑的操作細節已存在於 [[人工智能盲點審核卡]] 及 [[未明說的語境控制]]，不要在這裏再完整複製；
- 保持 [[人工智能盲點審核卡]] 為精簡目前任務工作輔助；如讀者在行動點需要，操作核查清單可在該處重複；
- 保持 [[未明說的語境控制]] 為未明說語境識別及處理次序的詳細權威；不要在其中複製規範風險到控制關聯圖；
- 保持 [[機構情境處理]] 為簡短導覽及工作例子橋樑；不要在其中複製完整七項處理路徑、完整保留準則或另一套詳細控制程序；以及
- 令 [[詞彙表]] 條目集中於術語意思及區別。如指引頁面已擁有詳細識別分類或操作程序，不要在詞彙表重複；以及
- 詞彙表例子保持概念性。例子可命名規範項目來說明概念，但不得列舉由 [[人工智能盲點控制圖]] 擁有的風險到控制、控制到方法、方法到控制或其他規範關聯集合。

#### 新集合

建立新的重複條目集合時，界定：

- 條目名稱及目的；
- 必備欄位或章節；
- 選用欄位或章節；
- 連結或相依；
- 審核要求；
- 維護要求。

#### 簡短路線及快速版本

快速開始路徑、摘要、分類、縮短核查清單或精簡配套路徑可簡化導覽，但不得建立批准權限、擴大適任性、削弱控制、移除來源／審核／升級處理／停止要求，也不得容許跳過專門領域、不確定、受限制、僅由人處理或多人流程。

精簡路線指向完整指引，不會取代完整指引或原文件內的任務專用控制。

不要只因完整指引內容較多便加入另一個縮短的公開文件。必須先取得：

- 來自具代表性讀者或真實使用的證據，顯示需要較短路徑；
- 擁有人批准；
- 評估對套件、翻譯、導覽、驗證及維護的影響；
- 證明較短路線保留所有必須界線的證據。

#### 重組內容

改變結構，例如分組、縮短或重組內容，不得移除重要控制。

保留每項告訴讀者以下事項的指示：

- 使用哪個來源；
- 不應做甚麼；
- 甚麼必須保留在人工智能之外；
- 誰必須審核或批准；
- 何時停止或升級處理；
- 可以或不得記錄或保留甚麼。

重現框架、決策路徑、路徑清單、核查清單或已批准項目集合時，保留其已批准標籤及意思。如數量及次序屬模型一部分，必須保留。清楚說明項目是步驟、替代選項、準則或獨立控制。

### 9.6 BSG–UCG 參考相依

本子節說明何時一項重要 BSG 變更可能需要通知及審核 Win.Win 人工智能應用案例指南（UCG）。第 16.10 節說明如何執行影響審核。

## 10. 標題、粗體標籤及提示框

### 10.1 提示框類型

只在資料值得中斷正常閱讀流程並特別突出時，才選擇性使用提示框。

使用以下技術識別碼：

- `[!note]` 用於補充語境或解讀指引；
- `[!tip]` 用於選用的實用協助；
- `[!important]` 用於讀者不可忽略的要求；
- `[!warning]` 用於停止條件、禁止行動或升級處理觸發條件；
- `[!caution]`：只用於嚴重且可能無法逆轉的後果。

---

### 10.2 提示框規則

只要每個提示框都有清晰而不同的目的，一份文件或一個章節可以包含多於一個提示框。不要設定固定上限。

避免不必要重複、零碎指引、互相矛盾的提示框，或多個互相爭奪注意力的提示框。

檢查提示框的 Markdown 及 Obsidian 語法是否有效、識別碼是否小寫、目的是否清晰、位置是否恰當、GitHub 呈現是否可讀、連結及強制換行是否正確，以及使用比例是否合適。

不要用提示框取代結構標題或必須條目章節。

不要在多個文件重複相同的通用警告。把通用指引放在本指南，只在對讀者有實質幫助時保留文件專用警告。

除非提示框語法本身有意成為可複製內容的一部分，否則不要把提示框語法放在可複製的提示詞、問題或範本回應欄位內。

技術提示框識別碼保留英文。按需要本地化可見標題及內容。

**應使用**

```md
> [!warning] 依賴輸出前先停止
> 在指定的承擔責任審核者或專門領域審核者完成所需審核前，不要依賴輸出。
```

**應避免**

```md
> [!NOTE]
> 重要資料。
```

第二個例子使用大寫識別碼，而且沒有解釋所需行動。

## 11. 撰寫及淺白語言規則

### 11.1 保留意思及控制強度

不要默默移除、合併、弱化或編造定義、區別、風險、控制、路徑、限制條件、審核要求、批准條件、升級處理邊界、例子、範本欄位或可重用習慣。

**縮短或重組清單時。** 當縮短、改述、重新排序，或把義務、條件、例外、路徑、保障措施或受控選項的清單轉為項目符號時，須交代來源中的每個實質項目。除非修訂後的措辭清楚保留所有重要區別，否則不要用一個寬泛的總括詞語取代幾個不同項目。對經實質重組的清單，審核證據應顯示每個實質來源項目保留於何處。

**重用規範清單時。** 當權威登記表提供完整選項集或規範清單時，判斷相關頁面需要完整集合，還是只需要簡短導向提示。如重現完整集合，須保留完整集合及其各項區別。如只需導向，提供明確並非規範定義的簡單語言提示，並連結至權威登記表。不要建立看似規範但不完整的清單，也不要建立第二個看似權威的定義。

---

### 11.2 淺白語言

優先使用具體動詞、已命名角色、已命名來源、清晰條件及直接後果。如果可以明確指出實際檢查，不要使用「小心審核」等含糊指示。

為可能剛接觸人工智能管治的讀者撰寫。面向讀者的頁面應適合大約 20–80 歲的一般成年讀者；他們熟悉使用生成式人工智能，但可能過度信任看起來完善或有信心的人工智能輸出。

支援辨識和記憶，而不是要求讀者先學習術語。讀者應能遇到不熟悉的受控術語，從附近的簡單語言指引理解實際概念，並在該受控術語再次出現時辨認出來。在實際可行情況下，加強 **人工智能盲點風險 → 相關控制 → 適用方法或指引 → 需要時的問責路徑 → 決定** 這條路徑，但不要把每個頁面都變成重複的工作流程。

使用 **有目的的重複**。當重複有助辨識或安全使用時，可重複簡短而穩定的記憶提示、受控名稱、決定標籤及行動點核對。不要在多個面向讀者的頁面反覆教授同一套長篇程序、分類、關聯圖、保留準則或詳細解釋。

## 13. 中文 Markdown 規則

### 13.1 強調標記空格

正確：

```md
這是一個 **重要提醒**。
这是一个 **重要提醒**。
```

不要在強調標記與中文標點之間加入不必要的空格。

正確：

```md
**指令**、**規則**
（**重要**）
```

### 13.2 中文冒號及粗體標籤

粗體鍵值標籤使用：

```md
**標籤：** 內容
**标签：** 内容
```

冒號放在粗體標記內；同一行其後有內容時，在結束的 `**` 後加入一個 ASCII 空格。

### 14.2 分節線及空白行

此慣例只適用於非 README Markdown 檔案。儲存庫層級及語言資料夾的 `README.md` 檔案明確豁免。

在兩個標題層級套用緊接子標題例外：

- 當 H1 與緊接的首個 H2 之間沒有正文內容時，不要在兩者之間加入主題分隔線；
- 當 H2 與緊接的首個 H3 之間沒有正文內容時，不要在兩者之間加入主題分隔線。

如父層標題與子層標題之間有正文內容，只在子層標題前加入一條主題分隔線。

其後每個 H2 前都必須剛好有一條主題分隔線，不論前面是 H2、H3、H4、段落、清單、表格、提示框、程式碼區塊或其他正文內容。

其後每個 H3 如在正文內容之後開始，或緊接另一個 H3 或 H4，其前都必須剛好有一條主題分隔線。

正文內容包括段落、清單、表格、提示框、引用區塊、圍欄式程式碼、圖片、內容連結及其他面向讀者的材料。空白行、主題分隔線本身及完整 HTML 註解不算正文內容。

每條主題分隔線前後都使用剛好一個空白行。此規則適用於 **每一條有效的主題分隔線**，包括頁末／頁尾分隔線及緊接圍欄式程式碼後的分隔線，而不只是標題前的分隔線。不要連續使用主題分隔線，也不要在主題分隔線周圍加入多個空白行。

標題與其後內容之間使用一個空白行。不要在 H4 標題前加入主題分隔線。

**應使用**

```md
# 文件標題

## 1. 緊接的第一個主要章節
```

```md
## 2. 主要章節

### 2.1 緊接的第一個小節
```

```md
## 3. 主要章節

簡介文字。

---

### 3.1 新小節
```

**應避免**

```md
# 文件標題

---

## 1. 緊接的第一個主要章節
```

```md
## 2. 主要章節

---

### 2.1 緊接的第一個小節
```

### 14.3 GitHub 強制換行

GitHub 一般會把同一段落內連續的實體行合併。只有在有意要求分開顯示時，才使用兩個行尾 ASCII 空格。

常見情況包括聯絡資料、簽名行、反饋標籤及連結、成對的簡短指引行，以及頁尾署名。

不同語言不需要強制換行完全一致。按每個文件的預定呈現方式判斷。

**如兩行必須在畫面上分開，使用強制換行**

```md
Win.Win@Skybroad | winwin.skybroad@gmail.com  
版本 1.0 | 根據創用 CC 姓名標示 4.0 國際授權條款（CC BY 4.0）— 可自由分享及改編，需署名 Win.Win@Skybroad
```

如正常段落換行已足夠，不要使用行尾空格。

---

### 14.4 表格

表格標題應簡短並具描述性。

重新格式化時保留每一行的意思。檢查直線符號、強調、連結及換行能否正確呈現。

如果正文或核查清單更清晰，不要強迫把每個概念放入表格。

---

### 14.5 編碼及換行格式

使用不含位元組順序標記（BOM）的 8 位元 Unicode 轉換格式（UTF-8），使用換行字元（LF）作為行尾，並在檔案結尾只保留一個最後換行。報告混合或非預期的行尾格式。

不要更改未變更檔案的行尾、空白、換行方式或表格間距。

### 16.8 法律、法規、私隱及專業語氣審核

#### 搜尋甚麼

搜尋表示確定性的詞語，包括：

`always`、`every`、`never`、`cannot`、`only`、`automatically`、`constitutes`、`required by law`、`compliant`、`illegal`、`defaults to`、`will reject`、`will require` 及 `no recall`。

#### 如何評估每個結果

對每個匹配項目，判斷該陳述是否：

- 是穩定概念或強制管治界線；
- 取決於句子未述明的事實；
- 取決於現行法律、法規指引、平台功能、模型行為或機構安排；
- 暗示最終專門領域結論；
- 暗示確定的外部決定或後果；
- 應改用有條件、以來源為本的措辭；
- 需要當前權威來源、核對日期或合資格審核。

#### 文字變更後

確認：

- 風險庫、控制圖、審核卡、詞彙表、指引、範本、README、導覽或翻譯備註中沒有遺留過時措辭；
- 工作卡及範本所教導的風險及控制模型與其來源指引一致；

### 16.10 UCG 參考影響通知審核

第 9.6 節說明哪些 BSG 變更可能影響 UCG。本小節說明如何執行審核。

#### 審核前

1. 確認確切的目前 BSG 及 UCG 套件；
2. 以修訂後 BSG 套件作目前 BSG 意思的來源，並以目前 UCG 套件作參考目標；
3. 閱讀 BSG 的導向、範圍、術語、路徑、控制界線、未明說語境、情境處理、保留、審核者適任性及維護指引。

1. 識別符合第 9.6 節觸發條件的 BSG 變更；
2. 掃描目前 UCG 公開檔案中的正式名稱、配套說明、路徑、定義、使用條件、範本欄位、風險庫參考、翻譯對應、可用性陳述及相關範圍措辭；

3. 把任何實質影響通知擁有人；
4. 除非擁有人明確把 UCG 納入範圍，否則在只處理 BSG 的工作中不要編輯 UCG；
5. 保留 UCG 任務層面的控制及獨立可用性；
6. 每次套件審核均建立新證據，不要重用舊的出現位置登記表。

### 16.11 BSG 模型、風險、路徑及適任性審核

在整個套件確認：

- 擁有人目的下的讀者結果仍然清楚：一般生成式人工智能使用者毋須先閱讀詞彙表，也能識別人工智能盲點概念、理解相關風險的意思，並找到至少一條緩解路徑；
- 預期讀者反覆識別的術語使用一個穩定的受控英文形式，並在 Stage 2 前識別固定目標語言映射覆蓋；
- 每項規範風險都支援三個擁有人目的問題：可能出甚麼問題、為何重要，以及下一步做甚麼；
- 如未提供詳細緩解措施，風險至少指出相關控制、方法、問責路徑或其他已批准下一步；
- 首次使用旅程支援「**這可能是人工智能盲點**」這個備用識別，以及返回 Win.Win 人工智能盲點指南取得進一步指引的路徑；
- 人工智能盲點仍然比未明說語境更廣；
- 已批准的目前詳細重點句子仍然準確；
- 任務依據的意思獲保留；
- 來源位置、可表述性及可靠性仍然彼此不同；
- 人員、已批准紀錄、兩者或不清楚仍是來源位置選項；
- 受控的可表述性類別保持完整；
- 如重現完整七條最低限度目前任務路徑，次序仍按已批准次序；
- 保留仍是獨立的受管治決定；
- 檢索、擷取、引導提取、分類、路徑處理、審核及核實仍彼此不同；
- 擁有人確認不會自動構成獨立核實；
- 角色、適任性、能力、許可、獨立性及權限仍彼此不同；
- 規範風險名稱及決策標籤保持精確；
- 問題優先的風險架構保留風險專用的提示詞層面、審核者、僅由人處理、安全轉換及升級處理控制；
- 受保護例子、問題、觸發條件、欄位及可重用習慣仍可分開識別；
- 風險識別先引向控制選擇，再引向控制專用方法；
- 未明說的語境控制沒有被呈現為所有風險的通用第一個控制；
- 控制、方法及問責路徑保持不同，而每個規範名稱只對應控制圖中的一個登記表；
- 詞彙表界定架構概念，但不重複個別規範登記表的完整定義；
- 控制圖同時包含登記表條目結構標準及獨立的風險關聯條目結構標準；
- 每項規範風險在控制圖有一個風險關聯條目，解釋為何所列控制、方法及問責路徑可能相關；
- 控制圖區分最直接相關的控制與其他有條件控制，並且不把控制、方法及問責路徑呈現為沒有區別的一張清單；
- 風險庫風險條目不重複完整關聯圖；
- 未明說的語境控制不重現由控制圖擁有的規範風險→控制關聯圖；
- 由此開始教授簡短首次使用路徑，而不重現完整詳細的七路徑處理次序；
- 審核卡以先掃描格式呈現風險識別提示，並可保留審核期間需要的操作點核查清單；
- 機構情境處理維持短篇導向，而不是第二套詳細未明說語境程序；
- 詞彙表條目界定及區分術語，但不重現由其他頁面負責的冗長詳細識別分類或操作程序；
- 套件整體的重複內容用來強化短記憶提示或操作點安全，而不是反覆教導冗長查閱材料；
- 目前詳細範圍措辭把未明說的語境控制識別為目前詳細控制，同時保留「識別及安全引導提取未明說語境」作為最深入的實務處理；
- 檢索、擷取及核實仍彼此不同，包括在任何結合檢索及擷取的方法內；
- 未經擁有人批准架構，不加入推測性的更高層控制分組。

### 16.12 發現嚴重程度

`P1` 及 `P2` 是受控的發現嚴重程度標籤。它們不是 Purpose、Permission 或 Proof 的縮寫。

**P1** 用於已確認會影響意思、權限、批准、問責、私隱、法律或專業界線、發布身分、必要連結、Markdown 呈現或風險處理的問題。

如已確認問題涉及術語、結構、英式英語拼法、清單標點、連接詞、發布格式、共用樣板文字、必備強制換行、標題、表格、導覽、release、版本、frontmatter 或中文發布慣例，但不會改變核心管治意思，使用 **P2**。

如證據、配對、來源權威、專門領域術語、翻譯意思、審核者適任性、擁有人意圖或預定呈現仍不確定，使用 **僅供審核**。

### 16.13 整體狀態

只有在沒有任何可執行發現，而且獲授權執行邊界內所有必備確定性及語義檢查均已完成時，才使用 **PASS**。

當沒有已確認的修正阻礙，但仍有擁有人、雙語、專門領域、機構、代表性讀者、配對、術語、release 或發布決定未解決時，使用 **REVIEW REQUIRED**。

當已確認的可執行問題仍存在，或必備輸入、擷取、解碼、結構、術語、字體、連結、身分、release、版本或 P1 呈現問題妨礙可靠完成時，使用 **FAIL**。

#### 翻譯就緒關卡

不要把乾淨的驗證器結果、作者自我審核或擁有人略讀本身視為英文套件已可進入 Stage 2 翻譯的證明。在擁有人宣告英文套件 **TRANSLATION READY** 前，對該確切套件要求以下所有項目：

1. 沒有未解決 P1 或 P2 發現；
2. 對每個範圍內非 README 公開頁面完成逐頁新讀者及 TC 翻譯壓力測試；
3. 至少一次審核者中立的獨立審核，判斷套件是否符合擁有人目的接受準則，並明確說明任何抽樣限制；
4. 所有可執行語義發現均已修正，或由擁有人明確接受為不變更決定；
5. 受管治術語覆蓋已與擁有人指定外部術語權威核對，沒有未解決受控術語缺口；
6. 作者及編輯指南、審核工具包、驗證器、翻譯備註及跨檔案導覽均已按最終英文內容重新評估；
7. 最終套件、權威、工具及證據身分按內容雜湊／版本記錄，而不是只依賴上載外層檔名；及
8. 擁有人明確宣告這個確切英文套件為 **TRANSLATION READY**，並指定為凍結 Stage 2 來源基準。

該宣告後任何英文來源變更都會重新開啟 Stage 1，並需要新的 Stage 2 基準取代原基準，而不是在翻譯階段靜默修正。

## 17. 維護及變更控制

### 17.1 共用規則

把共通的編輯、結構、本地化、驗證、版本、封裝、發布、證據及報告規則集中保留在本檔案，不要在每個公開檔案重複。

對擁有人確認的每項差異，評估現有控制為何會容許問題出現。在實際可行時，加入或加強預防性的撰寫規則、審核規則、驗證器檢查、測試或控制組合。不要只修正目前檔案便結束一類會重複發生的差異。

對 **每項修正或完整套件變更**，明確重新評估本作者及編輯指南、目前審核工具包及目前驗證器是否需要相應更新。如現有控制已覆蓋問題，記錄 `no change required`；不要只為製造版本變動而更新元件。

---

### 17.2 文件專用規則

只有當個別檔案有特定相依關係時，才保留 `Maintenance and Change Control` 章節，例如穩定的連結條目名稱、其他地方採用的規範措辭、風險庫與控制圖對齊、審核卡同步、範本欄位對齊、受保護例子或審核者適任性控制。

---

### 17.3 相關參考文件

只有當原有或獲批准內容具有真實而有用的跨文件關係時，才加入「相關參考文件」。不要只為對稱而加入空白或推測性章節。

不要把領英系列、文章、培訓課程、未發布說明、簡報或其他外部評論，變成理解或安全使用本指南的先決條件。外部材料可以介紹、說明、解釋或推廣本指南，但每項必須指示、控制、界線、路線及停止條件都必須保留在已批准公開套件內。

撰寫重要定義、控制、例子、界線、角色、風險、路徑、決定及指示時，確保它們在目前發布之後仍然有用。

不要把長期適用的指引寫成臨時發布說明、未來承諾或未發布計劃。

不要說另一份指南、語言版本、快速版、培訓資源或支援文件已存在，除非它已獲批准、發布及連結。如擁有人批准提及未來工作，清楚說明它尚未提供，而且理解或安全使用本指南並不依賴該未來工作。

---

### 17.4 審核周期

按既定時間表，以及在工具、政策、法律、機構角色、來源系統、工作流程、安全控制、風險暴露、語言、術語權威、審核者適任性安排或 BSG–UCG 相依關係有實質變更後，審核機構自訂版本及已發布指南的維護情況。

---

### 17.5 Frontmatter

除非獲授權進行受控遷移，否則保留既定 frontmatter 欄位及次序。

常見欄位包括：

- `title`；
- `created`；
- `updated`；
- `version`；
- `tags`；
- `status`；
- `type`；
- `source-role`；
- `locale`；
- `licence`。

保持 `created` 不變。

每份已修改的公開文件都必須包含 `updated` 欄位，並把它設為擁有人批准的修正日期。如該欄位不存在，應予以新增。

不要更改其他內容不變文件的 `updated` 欄位。未修改的文件必須保持位元組完全相同。

只為更新 `updated` 而變更檔案屬於缺陷。

Frontmatter 標籤及簡短標籤式中繼資料值毋須以句號結尾。不要只為視覺一致而加入標點。

---

### 17.6 文件版本

文件版本屬於一個公開文件。

首次發布前：

- 每個現有公開檔案維持版本 `1.0`；
- 發布前的編輯、結構、翻譯、排版、證據、驗證或封裝修正，不要遞增版本；
- 只有擁有人明確開始新的已發布文件版本時才更改版本。

發布後：

- 只變更擁有人批准版本更新所包括的文件；
- 未變更檔案維持現有版本；
- 每個頁尾版本與 frontmatter 版本完全一致。

使用擁有人就該作品及語言批准的標準頁尾。

對目前 BSG 套件，每個非 README 公開 Markdown 檔案都必須使用已批准的短標準頁尾。`README.md` 是已有文件角色規則的例外，因為它使用自己的已批准導覽、聯絡、儲存庫路徑及授權條款頁尾結構。不要只為視覺對稱而把短標準頁尾加入 README。

在 `en_HK` 中，使用已批准、包含 `CC BY 4.0` 的簡短英文授權條款措辭。

在已發布的 `tc_HK` 及 `sc_HK` 版本中，於相應頁尾使用完整已批准的繁體中文或簡體中文授權條款名稱，後接 `（CC BY 4.0）`。

授權條款措辭可遵循已批准的 Win.Win 共用模式，但版本號必須始終與目前 BSG 檔案本身的 frontmatter 版本相符。不要從其他成品、語言檔案、套件或例子複製版本號。

把已批准頁尾措辭視為受控共用樣板文字。除非擁有人明確批准新的頁尾模式，否則不要縮短、擴展、重新翻譯或以其他方式改動。

文件版本與套件發布版本分開。

### 17.7 套件發布及發布歷史

套件發布是完整作品的已發布快照。

首次發布前，除非擁有人明確更改，套件發布版本維持 `1.0`。

發布版本號顯示於適用 README 文件。

發布後，一個 release 可包含不同文件版本的文件。

記錄對讀者有實質影響的發布變更，例如：

- 新公開檔案；
- 實質的風險、控制、路徑、決定、權限或批准變更；
- 新語言資料夾；
- 實質套件重組；
- 重要的範圍、受眾或公開語言變更；
- 實質新增的維護或調整能力。

除非擁有人要求，細微排版、標點、自我指稱、證據、驗證或封裝修正毋須加入 release 歷史備註。

---

### 17.8 索引及導覽維護

新增、重新命名、移除或實質改變公開文件用途時：

- 更新適用語言資料夾的 README 索引；
- 更新相關導覽檔案及讀者路徑；
- 每個 wikilink 使用確切本地檔名；
- 如已有翻譯，保留既有本地化命名模式；
- 說明檔案協助讀者理解或做甚麼，而不只是說明其檔案類型；
- 驗證每個新本地連結。

審核根目錄 `README.md` 是否受相依影響，並把任何問題報告給擁有人。BSG 作者不得修改它。

如 `en_HK/README.md` 在其他方面屬工作範圍，仍須精確保留其受保護 Master Source 提示框。導覽、語言資料夾、中繼資料或發布變更均不得改動該提示框。

### 17.9 公開套件與證據分離

公開壓縮檔只能在 `public/` 包裝資料夾下包含預定公開文件。

不要在公開壓縮檔內放置：

- 外部 `file_list.txt` 或同等檔案清單；
- 校驗和或雜湊清單；
- 審核報告；
- 驗證輸出；
- 變更登記表；
- 比較矩陣；
- 修正提示詞；
- 工具原始碼或測試；
- 證據檔案；
- 暫存文件。

對 BSG 套件及變更控制，使用直接 ZIP 清單，以及直接來源→最終路徑和位元組比較。

所有證據均放在公開套件之外。
