# 人工智能代理審批核查清單

**在人工智能可以單獨行動之前**

> [!note] **適用對象：**  
> 技術負責人、營運經理及考慮使用可採取自動化行動的人工智能工具的資訊科技能力職員。大多數剛開始使用人工智能的教會及小型組織暫時不需要此文件。如您僅使用人工智能起草文本供人工審核，請先從 [[3P 框架海報]] 及 [[人工智能安全核查清單 - 工作版]] 開始。

> [!quote] 關鍵區別：  
> 標準人工智能工具只作回應。但人工智能代理會作行動。  
> 在您賦予人工智能發送訊息、更新記錄、預約會議、提交表格或進行購買的能力之前 — 您需要不同的控制措施。此核查清單就是這些控制措施。

**本核查清單用途：** 針對任何可採取行動的人工智能系統（不僅僅是生成文本）的結構化審批關口。

**本核查清單非：** 通過評分即代表代理安全或將正確運作的保證。代理式人工智能引入了標準文本生成所沒有的真實風險。此核查清單降低這些風險 — 但不消除它們。

---

## 1. 代理與標準人工智能使用的區別

標準人工智能使用：您提供輸入 → 人工智能生成文本 → 人手閱讀並決定如何處理。

人工智能代理：人工智能可採取行動 — 發送電郵、更新記錄、預約會議、提交表格，或發布社交媒體 — 通常每個步驟有限或無需人手批准。

**組織環境中代理式人工智能的示例：**
- **自動回覆電郵** — 自動閱讀並發送回覆
- **自動預約** — 代表您預約會議室或預約
- **記錄更新** — 根據對話更新客戶管理系統、試算表或數據庫
- **自動廣播** — 自動發布社交媒體或發送訊息廣播
- **表格提交** — 無需人手確認即可提交表格、申請或訂單
- **多步驟工作流程** — 研究 → 起草 → 發送 → 跟進

**為何代理需要不同的控制措施：** 使用標準人工智能工具時，您在任何事情發生前會看到輸出。使用代理時，行動可能已在您注意到之前採取。錯誤可能在多個步驟中傳播。逆轉它們可能困難或不可能。

> [!important] 首先詢問此問題：  
> 此工作流程能否透過設計良好的提示詞及人手點擊發送來實現 — 而非完全自主的代理？  
> 許多看似需要代理的工作流程，透過良好的提示詞及人工審核機制同樣運作良好。  
> 如是 — 使用更簡單的方法。代理會放大價值與風險。

## 2. 四個代理風險維度

| 維度 | 問題 | 為何重要 |
|------|------|----------|
| **可逆轉性** | 如代理犯錯，能否逆轉？ | 發送的訊息無法撤回。刪除的記錄可能無法恢復。 |
| **影響規模** | 如出錯，會影響多少人或系統？ | 代理發送電郵給一個人與發送給整個會眾的區別。 |
| **可見性** | 您能否看到代理做了什麼、何時、為何？ | 如無審計追蹤（記錄人工智能做了什麼、何時、為何 — 以便調查錯誤），錯誤在後果出現前不可見。 |
| **授權** | 是否有人明確批准每種行動類型？ | 代理不應採取其操作者未有意識批准的行動。 |

## 6. 強制人手批准觸發條件

以下行動類型必須始終要求明確人手批准後方可執行，無論代理的置信度如何：

- [ ] **外部通訊** — 電郵、訊息、通知或社交媒體
- [ ] **財務記錄** — 交易、發票或付款的修改
- [ ] **人員記錄** — 人員、人力資源或成員記錄的更新
- [ ] **獲取或福利** — 任何影響人員資格、關顧或獲取的行動
- [ ] **不可逆轉行動** — 發送電郵、刪除記錄或提交表格
- [ ] **高成本錯誤** — 聲譽、財務、法律或關係風險

## 7. 失敗模式分析

在部署前，識別此特定代理最可能的失敗模式。

| 失敗模式 | 描述 | 風險等級 | 緩解措施 |
|----------|------|----------|----------|
| **提示詞注入** | 文件中的惡意內容指示代理採取意外行動 | 中–高 | 淨化輸入；限制代理讀取內容；行動前驗證輸出 |
| **目標誤解** | 代理以意外方式解釋模糊指令 | 中 | 編寫精確、有界限的指令；部署前測試邊緣情況 |
| **級聯錯誤** | 多步驟工作流程中的早期錯誤向下游傳播 | 高 | 在步驟間添加人手檢查點 |
| **範圍漂移** | 代理存取超出其預期範圍的數據或系統 | 高 | 應用最小權限：僅授予具體所需的存取 |
| **幻覺行動** | 代理捏造其認為已獲授權的決策 | 中 | 記錄所有行動；實施回滾（逆轉人工智能所為）；要求人工審核日誌 |
| **過度自信** | 代理在無不確定性機制的情況下以低質素輸出繼續 | 中 | 內建不確定性門檻；低於門檻時要求人工審核 |

**針對您的特定代理 — 識別最可能的 3 種失敗模式：**

| 失敗模式 | 可能性？ | 如發生有多嚴重？ | 計劃的緩解措施 |
|----------|----------|----------------|----------------|
| | 高 / 中 / 低 | 高 / 中 / 低 | |
| | 高 / 中 / 低 | 高 / 中 / 低 | |
| | 高 / 中 / 低 | 高 / 中 / 低 | |

| # | 問題 | 是 | 否 | 備註 |
|---|------|----|----|------|
| G1 | **可解釋邏輯** — 決策邏輯可向非技術持份者解釋？ | ☐ | ☐ | |
| G2 | **最終用戶已培訓** — 了解代理的能力及限制？ | ☐ | ☐ | |
| G3 | **反饋途徑** — 用戶可報告問題或建議改進？ | ☐ | ☐ | |
| G4 | **已考慮偏見** — 代理設計中的公平性及可及性？ | ☐ | ☐ | |
| G5 | **行動可區分** — 在共享系統中代理的行動與人手的行動分開？ | ☐ | ☐ | |
| G6 | **季度審核** — 定期週期（至少每 3 個月）檢查目標漂移？ | ☐ | ☐ | |

> [!note] 代理必須至少每 3 個月審核一次，以確保無目標漂移 — 即範圍逐漸擴展超出原本預期。

## 9. 試點設計

代理式人工智能應始終在更廣泛部署前從有界限的試點開始。

| 欄位 | 您的答案 |
|------|----------|
| **試點範圍** | 將測試哪些具體行動子集？ |
| **試點環境** | 真實數據/真實系統，或測試環境？ |
| **試點持續時間** | |
| **人手監督** | 人手將如何監控代理的行動？ |
| **成功標準** | 成功的試點是什麼樣子？ |
| **停止標準** | 在何種條件下將停止試點？ |
| **擴展前簽署** | 誰必須批准從試點轉向更廣泛使用？ |

## 10. 禁止的代理用途 — 始終超出範圍

- [ ] **牧養通訊** — 信仰、危機或輔導訊息：僅限牧師或負責人處理
- [ ] **人力資源決策** — 僱傭、紀律、薪酬或績效：絕不由代理執行
- [ ] **財務承諾** — 承諾資金、批准開支或啟動付款：需人手批准
- [ ] **法律提交** — 提交、遞交或回應法律或監管文件：絕不由代理執行
- [ ] **受益人決策** — 任何服務或福利的資格、獲取或優先次序：絕不由代理執行
- [ ] **健康通訊** — 提供、推薦或根據健康相關資訊行動：絕不由代理執行
- [ ] **大量個人資料** — 匯出、刪除或轉移大量個人資料：需明確人手授權

## 11. 受保護工作流程模式

受保護工作流程在正確位置內建人手檢查點：

```
受保護工作流程模式

步驟 1：代理收集資訊/研究/起草
        |
步驟 2：[人手檢查點] — 人工審核代理計劃或草稿
        | 已批准
步驟 3：代理執行低風險步驟（例如創建內部草稿）
        |
步驟 4：[人手檢查點] — 人手在任何外部行動前審核
        | 已批准
步驟 5：代理執行 或 人手執行外部行動
        |
步驟 6：代理記錄行動並向人手確認
```

**最低所需檢查點：**
- **外部發送前** — 任何外部通訊
- **數據更改前** — 生產系統中任何數據修改
- **財務行動前** — 啟動任何財務行動
- **意外情況** — 當代理遇到超出範圍的情況時

## 13. 香港特定考慮

- [ ] **《個人資料（私隱）條例》原則 3** — 如代理處理個人資料，已評估合規性
- [ ] **外部通訊** — 未經同意不包括第三方的個人資料
- [ ] **教會背景** — 牧養內容、祈禱事項及輔導記錄明確排除
- [ ] **第三方平台** — 已審核數據駐留及私隱條款
- [ ] **受規管實體** — 如為證監會或金管局實體營運，需要額外監管審核

## 14. 給組織的代理備註

對於大多數組織，近期有意義的人工智能代理使用案例是：
- **會議轉錄** — 摘要並由人工審核輸出
- **電郵草稿生成** — 由查詢觸發；人手批准後發送
- **文件問答** — 有需要時可交人手跟進

完全自主的代理 — 無需每步人手批准即可發送通訊、更新記錄或做出決策的代理 — 有更顯著的風險，通常不適合沒有專職資訊科技管治能力的組織作嘗試。

**原則：** 從解決真實問題的最簡單方案開始。許多看似需要代理的工作流程，透過設計良好的提示詞及人手點擊發送同樣運作良好。
