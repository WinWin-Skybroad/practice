# Choosing Your First Use Case

## 1. Purpose and Scope

Start with a use case that is easy to review, easy to contain, and easy to reverse.

Do not start with the most impressive AI project just because it sounds transformative. Start with a task where the organisation can learn the review habit safely.

If you are using AI for your own administrative tasks rather than on behalf of an organisation, the same use-case pages still apply. Treat the owner, reviewer, and approver labels as responsibilities that may be held by you only where the task is low-consequence and within your competence and authority.

Where the page requires independent checking, specialist competence, or approval by another responsible person, self-review is not sufficient. Ask an appropriate person with the required knowledge or authority. If no suitable reviewer is available, pause the task or keep the output as an unapproved draft rather than treating it as final.

---

## 2. Good First Use Cases

Good first use cases are usually:

- boring rather than impressive
- low visibility if wrong
- easy to check against a source document, record, or meeting note
- reversible before external harm
- owned by a named person
- small enough to pilot
- easy to train with one real example

Examples include meeting summaries, internal communications, simple bilingual drafts, and document summaries where the source can be kept open during review.

---

## 3. Poor First Use Cases

Poor first use cases are usually:

- public-facing before review is possible
- difficult to reverse after a mistake
- connected to legal, HR, finance, privacy, regulatory, safeguarding, counselling, pastoral, theological, or other specialist matters
- dependent on unclear authority or sensitive context
- agentic or automated in a way that takes action without a human gate
- too large for one owner to supervise during the pilot

Do not treat these as permanently rejected. Many should be marked **not yet** until review, ownership, escalation, and stop rules are ready.

---

## 4. First-Use-Case Test

Before choosing a first use case, ask:

1. If this goes wrong on day one, who finds out?
2. Can the mistake be corrected before it reaches an external audience?
3. Can the output be checked against a reliable source?
4. Is there a named owner and reviewer?
5. Is the task small enough to pause if the review process does not work?

If the answer to any question is unclear, choose a smaller or more reviewable use case first.

---

## 5. Decision Record

For the first use case, record:

- selected use case
- owner
- reviewer
- review method
- escalation route
- whether the task is approved, conditional, not yet, or stopped
