# First Mistake Review

## 1. Purpose and Scope

When the first AI mistake happens, do not only tell the reviewer to be more careful.

Treat the mistake as information about the workflow.

---

## 2. Review The Design, Not Only The Person

Ask:

1. Was this use case suitable for AI assistance?
2. Was the prompt clear enough for the task?
3. Was the source packet current, approved, and complete?
4. Was the reviewer matched to the specific risk?
5. Did task volume make review too thin?
6. Was the escalation route clear and usable?
7. Did the output touch a risk that should move the use case from approved to conditional, not yet, or stopped?

---

## 3. Common Design Causes

| Symptom | Possible design cause |
|---|---|
| Wrong fact passed review | Source was outdated, incomplete, or not checked against the right record. |
| Sensitive content appeared | Source packet or prompt did not define what must be excluded. |
| Reviewer approved outside authority | Escalation route or approval boundary was unclear. |
| Same error repeats | Correction was not built back into the prompt, template, workflow, or review method. |
| Review became a skim | Volume increased without review capacity or sampling rules. |
| AI answer changed after user challenge | User-pressure drift was not checked against a source. |
| AI checking AI was treated as verification | Independent source checking was missing. |

---

## 4. After The Review

Decide whether to:

- keep the use case approved with a corrected workflow
- make it conditional until a gap is fixed
- pause the pilot
- escalate the use case to a responsible owner
- stop the use case because the risk cannot be controlled in the current organisation

---

## 5. Practical Rule

The first mistake is a design signal. Use it to improve the workflow before the same weakness returns in a different form.
