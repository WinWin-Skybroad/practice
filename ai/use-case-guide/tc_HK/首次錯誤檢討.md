# 首次錯誤檢討

## 1. 目的及範圍

第一次出現人工智能錯誤時，不要只叫審核者再小心一點。

要把錯誤視為工作流程提供的資訊。

---

## 2. 檢討設計，而不只是檢討個人

請問：

1. 這個應用案例是否適合使用人工智能協助？
2. 提示詞是否足夠清楚，適合這項任務？
3. 來源資料包是否最新、已批准及完整？
4. 審核者是否與特定風險相配？
5. 任務量是否令審核過於粗疏？
6. 升級處理路徑是否清楚而且可用？
7. 輸出是否涉及某項風險，令應用案例應由已批准改為有條件批准、尚未適合或停止？

---

## 3. 常見設計原因

| 現象 | 可能的設計原因 |
|---|---|
| 錯誤事實通過審核 | 來源過時、不完整，或沒有對照正確記錄核對。 |
| 出現敏感內容 | 來源資料包或提示詞沒有界定必須排除的內容。 |
| 審核者在權限範圍外批准 | 升級處理路徑或批准界線不清楚。 |
| 同一錯誤重複出現 | 更正沒有回寫至提示詞、範本、工作流程或審核方法。 |
| 審核變成快速略讀 | 工作量增加，但沒有相應審核能力或抽樣規則。 |
| 使用者提出質疑後，人工智能答案改變 | 沒有對照來源檢查用戶施壓導致偏移。 |
| 把人工智能檢查人工智能當作核實 | 缺少獨立來源核對。 |

---

## 4. 檢討後

決定是否：

- 保持應用案例已批准，但修正工作流程
- 在修正缺口前改為有條件批准
- 暫停試點
- 把應用案例升級交由責任負責人處理
- 因目前機構無法控制風險而停止該應用案例

---

## 5. 實用規則

第一個錯誤是一個設計訊號。應利用它改善工作流程，避免同一弱點以另一種形式再次出現。
